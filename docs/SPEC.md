# Urban Design Harness — 시스템 명세 (정본)

> 이 문서가 본 플러그인의 정본 명세다. 모든 구성요소(스킬·에이전트·커맨드·템플릿)는 이 명세를 따른다.

## 1. 정체성과 핵심 원칙
도시설계 모듈은 프롬프트·프로토콜·페르소나·에이전트 지침이 종합된 하나의 하네스다. 표면 산출물은 판넬이지만, 이면의 개념·아이디어·논리가 문서로 명세되고 버전 관리되어야 한다.

### 1.1 불변 원칙
- **판넬 중심** — 모든 결과는 판넬로 표현되고, 판넬만 봐도 설명이 되어야 한다. 이면은 전부 고려·기록된 상태여야 한다.
- **명세 우선** — 판넬 각 섹션은 백그라운드 문서로 명세하고 버전 관리한다. 새로 추가된 내용을 추적한다.
- **단일 귀결** — 모든 논리 구조는 상위의 단 하나의 방향성 문서(DIRECTION.md)로 귀결된다.
- **논리적 서술 의무** — 결론만 두지 않는다. "기존 문제 → 무엇을 바꾸는가 → 어떤 영향"의 서술 과정 필수.
- **피드백 루프 필수** — 각 단계 종료 시 방향성 재검토. 더 나은 안이 나오면 논리 구조를 다시 세운다.
- **무결성 검증** — 최신 버전은 무결성 검증 통과 후에야 방향성 문서로 귀결된다. 연결 문서와 모순 0.
- **레퍼런스 기반** — 방법론·분석론·도구·배치·색상 등 모든 판단에 레퍼런스가 따라야 한다.
- **완결 세트 선행** — 시작 시 스토리·서술·주제를 완결 세트로 확정해 사후 끼워맞춤을 차단한다.
- **사후 개선 수용** — 진행 중 더 나은 안의 발견은 자연스러운 일이며 피드백 루프로 흡수한다.

### 1.2 비약 금지 규칙 (가드레일)
불확실한 부분은 논리적으로 비약하지 않는다. 근거 없는 가정 대신 **🔲 미결정**으로 표기하고 사용자에게 질의한다. verify 에이전트가 강제한다.

## 2. 프로젝트 구조
인스턴스 1개 = cwd 1개. CLAUDE.md 자동 로드, direction/(방향성 SSOT)·panel/(섹션 명세)·process/(단계 작업)·design_system/·references/·assets/·_state/(동적 상태). 모든 기록은 **로컬 파일 기반** — 외부 서비스 의존 없음.

## 3. 프로세스
1) 대상지 선정 → 2) Site Analysis → 3) Comprehensive Analysis(이슈 도출→이유→영향, 시각화 중요) → 4) Design Process(요소별 문제→변경→영향 서술) → 5) Master Plan(contour 기반 3D, 1인칭·조감 다중 뷰). 각 단계 간 피드백 루프.

### 섹션 단위 작업 파이프라인
① 섹션 진입(PANEL_SPEC 좌표·크기) → ② 논리 구성(최우선) → ③ 텍스트 구성 → ④ 디자인 협업(시각화 형태·템플릿) → ⑤ 판넬 반영(영역 맞춤 SVG/이미지) → ⑥ 섹션 SPEC 갱신 → 피드백 루프.

## 4. 에이전트 6종 (서브에이전트 위임 방식)
| 에이전트 | 역할 |
|---|---|
| architect (메인) | 주도. 섹션별 논리→텍스트→판넬 반영 |
| design | 템플릿·영역·크기 — 판넬을 디자인으로 구성 |
| verify | 루프마다 당위성·무결성·방향성 검증, 비약 차단 |
| research | 분산 데이터 점진·순차 수집, 더 나은 안 발견 시 루프 트리거 |
| modeling | 3D 도구(SketchUp 등) 전용 표현 |
| critic | 제3자(심사자) 시점 냉철 비평 |

통신: 오케스트레이터가 Agent 도구로 서브에이전트 위임 호출 (단일 세션 내).

## 5. 문서 관리
- 트리 구조: DIRECTION.md(최상위) → 섹션 명세 → 레퍼런스/하위 자료. 꼬리물기 축적.
- 버전: 직접 변경 +0.1 / 간접(전파) 변경 +0.01. 타임스탬프 의무. 맥락 구분(이전/현재/진행중/보관).
- 최신 버전은 verify 통과 후에만 DIRECTION.md 귀결.
- 사용 도구·방법론에 출처가 있으면 백그라운드에 상세 명세.

## 6. 디자인 시스템
DESIGN.md = 디자인 아이덴티티 단일 기준. templates/ = 정보 유형별 시각화 템플릿 라이브러리. 색상 체계는 프로젝트별로 레퍼런스 수집 후 결정.
도구 선택: 인간 개입 정도에 따라 적합성을 판단한다. ⚠️ 생성형(렌더링) 이미지는 기관·수업·공모전 규정에 따라 제한될 수 있다 — 인스턴스 정책으로 확인 후 사용.

## 7. 레퍼런스 수집
references/INDEX.md에 출처·분류·태그 인덱싱, 주제별 하위 폴더 보관. research 에이전트 주도, 관련 섹션 문서 하위로 연결.

## 8. 피드백 루프 & 무결성
작업 → 방향성 업데이트 → verify(당위성·무결성) → 통과: DIRECTION 귀결+버전 기록 → critic 비평 / 불일치: 논리 구조 재구성. 검증 결과는 _state/integrity-report.json. 시스템의 본질: 역할들이 기록을 남기고 → 기록이 방향성을 형성하고 → 지속 체크로 구조가 무너지지 않게 관리.
